## 1. Executive Summary

### Overall rating: **9.7 / 10**

Rooney has continued to mature significantly since the previous review. The latest revision adds a substantial Markdown rendering expansion while preserving the strong asynchronous architecture, Unicode-aware text handling, viewport virtualization, Tree-sitter generation tracking, and search/Markdown stale-result protection established in earlier sessions.

The biggest improvement is the transition from flattened Markdown text to structured inline spans, enabling richer rendering of:

- bold
- italic
- inline code
- strikethrough
- links
- image fallbacks
- GFM tables
- task lists
- alerts
- footnotes
- HTML fragments such as `<br>` and `<img>`

The main reason the score is slightly below the previous 9.85/10 is not a regression in the core editor architecture. It is that the new Markdown parser/renderer introduces a few semantic gaps that should be addressed before describing the Markdown implementation as fully compliant.

The most important newly identified issue is **nested-list handling**, where the shared inline collector can cause parent list-item content to be lost when a nested list begins.

# 5. P1 — Nested List Content Loss

The most important issue found in this review is nested-list handling.

Consider:

```markdown
- Parent item
  - Child item
```

The current parser shares an `InlineCollector`.

The sequence can effectively become:

```text
Parent item
↓
nested List starts
↓
collector reset
↓
Child item
```

As a result, the parent's inline content can be discarded when the nested list begins.

The intended structure:

```text
Parent
└── Child
```

can instead degrade into something equivalent to:

```text
Child
```

This is not merely an unsupported feature. It can result in Markdown content being lost during parsing.

### Recommended fix

Use a stack of list contexts, with each list/list-item level retaining its own collector.

Conceptually:

```rust
struct ListContext {
    depth: usize,
    collector: InlineCollector,
    task_status: Option<bool>,
}
```

Then:

```text
List start
  ↓
push context
  ↓
ListItem start
  ↓
nested List
  ↓
push child context
  ↓
child end
  ↓
pop child context
  ↓
restore parent context
```

This should be treated as the highest-priority Markdown fix.

# 6. P2 — Nested Inline Formatting

The current inline collector tracks:

- strong depth
- emphasis depth
- strike depth

but stores content in separate buffers.

That makes nested formatting such as:

```markdown
**bold *and italic***
```

difficult to represent correctly.

A richer representation would be something like:

```rust
struct InlineStyle {
    bold: bool,
    italic: bool,
    strike: bool,
    code: bool,
}
```

combined with:

```rust
struct InlineSpan {
    text: String,
    style: InlineStyle,
}
```

This would make combinations of styles explicit rather than relying on precedence between separate buffers.

This is a P2 issue rather than a fundamental architecture problem.

# 7. Links Are Styled, But Not Yet Clickable

The current Markdown representation preserves link URLs:

```text
InlineSpan::Link {
    text,
    url,
}
```

and the UI can style them as links.

However, the reviewed implementation does not currently provide actual click handling that opens or navigates to the URL.

Therefore the implementation currently provides **styled links**, rather than fully **clickable links**.

Two reasonable options exist:

1. implement link click handling; or
2. change README wording so it does not claim clickable links.

# 8. GFM Compliance Wording

The README's wording around:

> Text-Focused GFM Compliant

is somewhat stronger than what the current implementation demonstrates.

Because nested lists and nested inline formatting are not fully represented, wording such as:

> Text-Focused GFM Support

or

> Text-Focused GFM Renderer

would more precisely match the current implementation.

The implementation clearly supports a substantial GFM subset, but "compliant" implies a broader semantic guarantee.

# 12. HTML Handling

The new lightweight HTML handling is appropriate for Rooney's architecture.

HTML fragments such as:

```html
<br>
<img src="..." alt="...">
```

can be converted into safe text-oriented representations.

Importantly, Rooney does not need to embed a WebView or execute arbitrary HTML/JavaScript merely to display Markdown.

The implementation should be understood as a **text-oriented HTML fallback parser**, not as a general-purpose HTML parser.

# 13. Background Alpha / Dimming

The new unified background rendering is a good architectural cleanup.

Background rendering now centralizes:

- alpha
- RGB dimming
- background semantics

instead of relying on separate overlay behavior.

This improves consistency between:

- editor
- Markdown view
- empty states

One caveat is that this changes compositing semantics somewhat, so real-world testing with translucent Wayland windows and compositor behavior remains worthwhile.

# 14. Tree-sitter Async Architecture

This remains one of Rooney's strongest areas.

The current generation-based architecture cleanly separates:

```text
parse_generation
markdown_generation
search_generation
```

Workers produce results tagged with their generation, and the UI applies results only when the generation still matches.

This protects against races such as:

```text
Worker A → Gen 10
user edits
Worker B → Gen 11
Worker A finishes
```

Worker A can safely be discarded.

The previous bug where a stale Tree-sitter completion could incorrectly clear `is_parsing_async` has also been fixed.

This subsystem is currently in very good shape.

---

# 15. Search

Search now uses generation tracking and correctly discards stale results.

Correctness is therefore strong.

The remaining issue is efficiency: large-file query typing can create multiple background workers for successive query states:

```text
c
co
cod
code
```

Generation checks prevent stale results from being applied, but older workers may still consume CPU.

A future latest-only worker queue, cancellation mechanism, or query debounce would improve efficiency.

---

# 16. Rope / Unicode

The text model remains one of Rooney's strongest components.

It combines:

- Ropey
- UTF-8 byte offsets
- grapheme-aware cursor movement
- grapheme-aware deletion
- Tree-sitter `InputEdit`
- cursor clamping
- Unicode-aware editing

This is substantially more robust than treating Unicode text as simple character arrays.

---

# 17. Undo / Redo

Undo/redo remains a relative weak point.

The current bounded snapshot approach limits the number of stored states, but each snapshot can still represent a large Rope.

Therefore:

> bounded snapshot count

does not mean:

> constant memory usage

For very large files, a sequence of edits can still consume significant memory.

A more precise documentation term would be:

> bounded-count undo/redo ring buffer

rather than wording that could imply O(1) memory usage.

---

# 18. Large-File Architecture

The hybrid architecture remains sound:

```text
<= 2 MB
    synchronous

> 2 MB
    debounce
    ↓
spawn_blocking
    ↓
generation validation
```

This keeps expensive parsing/searching away from the interactive editing path.

The main remaining limitation is that initial large-file loading is still synchronous.

Therefore the architecture should not be described as guaranteeing that every large-file operation is completely non-blocking.

More precisely:

> large-file incremental editing avoids synchronous heavy parsing on the input path.

---

# 19. Tree-sitter Full Parse Cost

Earlier benchmarks showed full parsing of a 50 MB document can still take on the order of tens of seconds.

The important distinction is that this is now primarily a **background throughput/CPU issue**, rather than a direct UI-freezing problem.

Background execution solves responsiveness, but does not eliminate the underlying computation.

This remains one of the technically strongest parts of Rooney.

# 21. Glyph Metrics

The main editor's use of `cosmic-text` glyph metrics and caching is strong.

It handles:

- non-ASCII measurement

Markdown table measurement is currently less precise, so eventually sharing the same typography measurement infrastructure would improve consistency.

Compared with the Markdown and editor rendering changes, this is currently lower priority.

# 27. Maintainability

The Markdown renderer has grown considerably, reaching roughly 766 lines in the reviewed source.

It now contains several distinct responsibilities:

- block parsing
- inline parsing
- HTML fragment handling
- Markdown AST representation
- rendering preparation

A future split such as:

```text
markdown/
├── mod.rs
├── parser.rs
├── inline.rs
├── html.rs
└── renderer.rs
```

would improve maintainability.

This is not an urgent defect, but it will become increasingly valuable as Markdown features continue to grow.

# 29. Final Evaluation

Rooney is now a mature Rust/COSMIC editor architecture rather than a small experimental editor.

Its strongest technical combination remains:

```text
Ropey
+
Tree-sitter
+
Unicode grapheme handling
+
cosmic-text glyph metrics
+
viewport virtualization
+
generation-tracked asynchronous processing
```

The new Markdown work is directionally correct and significantly improves the product's functionality and visual quality.

The main next step is **not another large feature expansion**.

The best next phase is stabilization:

1. fix nested Markdown semantics;
2. strengthen Markdown regression coverage;
3. align documentation with actual behavior;
4. profile memory and background CPU;
5. perform real GUI/IME/Wayland QA.

### Final rating: **9.7 / 10**

**Status: High-quality / near-release maturity, with targeted Markdown correctness work recommended before calling the Markdown implementation fully mature.**
